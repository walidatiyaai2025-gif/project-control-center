# Governance Laws

These laws are non-negotiable for every managed repository and every PCC Manager/Lead/Worker role.

1. NO REQUEST WITHOUT TASK ID.
2. NO CODING WITHOUT A TASK.
3. NO NEW TASK BEFORE DUPLICATE CHECK.
4. ONE LOGICAL TASK = ONE CANONICAL TASK BRANCH.
5. WORKERS MAY CHANGE; TASK IDENTITY AND CONTINUATION PATH MUST NOT.
6. NO UNTRACEABLE PRODUCTION BRANCH.
7. NO PR WITHOUT TASK TRACEABILITY.
8. NO DONE WITHOUT REQUIRED QA / INTEGRATION / RELEASE EVIDENCE.
9. STALE WORK IS RECLAIMED, NOT RECREATED.
10. CONTINUATION FIRST. NEW BRANCH LAST.
11. NO WORKER MAY PRESENT BRANCH-LOCAL PROGRESS AS PROJECT-WIDE PROGRESS.
12. OFFICIAL PROJECT STATUS MUST HAVE ONE CANONICAL SOURCE.
13. OFFICIAL BUILDS MUST BE GENERATED FROM CONTROLLED CI AND IMMUTABLE SHAs.
14. EXISTING PROJECTS MUST UNDERGO LIVE BASELINE DISCOVERY BEFORE GOVERNANCE IS IMPOSED.
15. NEVER DISCARD UNIQUE UNMERGED WORK TO SIMPLIFY BRANCH STRUCTURE.
16. UNTRACKED REQUESTS MUST TREND TO ZERO.
17. EVERY MANAGER/LEAD MUST READ ROOT `AGENTS.md` BEFORE DISPATCHING WORK.
18. NO IMPLEMENTATION DISPATCH WITHOUT AN AUTHORITATIVE PCC ROUTING PACKET.
19. PROJECT, CLIENT, VARIANT, AND CHANGE SCOPE MUST BE RESOLVED BY THE MANAGER/LEAD BEFORE IMPLEMENTATION.
20. NO WORKER MAY GUESS CLIENT OR VARIANT IDENTITY FROM A BRANCH NAME.
21. PRODUCT-FAMILY CORE CHANGES REQUIRE CROSS-VARIANT VALIDATION FOR ALL AFFECTED ACTIVE VARIANTS.
22. VARIANT-SPECIFIC CHANGES MUST NOT LEAK INTO SIBLING VARIANTS.
23. AMBIGUOUS OR CONFLICTING ROUTING IS A WRITE BLOCKER, NOT A DELEGATION TO THE IMPLEMENTATION WORKER.
24. MANAGER/LEAD RESPONSIBILITY CONTINUES THROUGH QA, INTEGRATION, RELEASE/DEPLOYMENT WHEN REQUIRED, AND FINAL EVIDENCE RECONCILIATION.
25. LIVE GITHUB STATE OVERRIDES STALE SHAS OR STATUS WRITTEN IN HISTORICAL PROMPTS/HANDOFFS.
26. DURABLE OPERATIONAL DECISIONS MUST BE PERSISTED IN PCC CONSTITUTION/POLICY; CONVERSATION ALONE IS NOT CANONICAL GOVERNANCE.
27. AN OWNER INSTRUCTION THAT AMENDS GOVERNANCE MUST BE ENCODED AND VALIDATED BEFORE DEPENDENT WORK RELIES ON IT; OTHERWISE RETURN `CONSTITUTION_AMENDMENT_PENDING`.
28. ADDING/ONBOARDING A PROJECT AUTOMATICALLY REQUIRES PCC MANAGER CLASSIFICATION AS `STANDALONE` OR `PRODUCT_FAMILY`.
29. PRODUCT-FAMILY ONBOARDING MUST ENUMERATE KNOWN VARIANTS/CLIENTS, ALIASES, IMPLEMENTATION-LOCATION STATE, ROUTING STATE, AND SHARED-CORE STATE.
30. NEVER INVENT A VARIANT DIRECTORY, PERMANENT CLIENT BRANCH, DEPLOYMENT TARGET, OR SHARED-CORE BOUNDARY TO SATISFY ONBOARDING METADATA.
31. A DECLARED BUT UNRESOLVED VARIANT REMAINS VISIBLE AND MUST BE ROUTING-BLOCKED FOR THAT BOUNDARY; VERIFIED SIBLING VARIANTS MAY REMAIN ROUTABLE.
32. VARIANT IMPLEMENTATION WRITES REQUIRE `ROUTING_STATE=READY`; CORE WRITES REQUIRE `CORE_ROUTING_STATE=READY`.
33. AN EXPLICIT OWNER REQUEST TO ADD/ONBOARD A REPOSITORY AUTHORIZES ONLY THE GOVERNANCE-ONLY ONBOARDING CHANGES DEFINED BY PCC; IT DOES NOT AUTHORIZE PRODUCT-SOURCE CHANGES OR DEPLOYMENT.
34. REPLACEMENT MANAGERS/LEADS MUST BE ABLE TO RECONSTRUCT CURRENT GOVERNANCE FROM COMMITTED PCC MAIN AND TARGET REPOSITORY CONSTITUTIONS WITHOUT CHAT MEMORY.

## Canonical traceability chain

OWNER REQUEST → PCC CONSTITUTION → PCC ROUTE → PORTFOLIO → PROJECT/FAMILY → VARIANT (when applicable) → REQUIREMENT → TASK → BRANCH → COMMIT → PR → CI → QA → INTEGRATION → RELEASE/DEPLOYMENT (when required) → USER ACCEPTANCE.

Any broken link is a control-plane defect and blocks authoritative DONE where that link is required.
